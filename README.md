# Event Management API — Автоматизация организации мероприятий

**Роль:** бизнес-аналитик  
**Предметная область:** организация мероприятий 
**Основной фокус:** анализ бизнес-процессов, управление требованиями, бизнес-правила, критерии приёмки, прослеживаемость и проверка API-контракта.

> **Статус проекта и границы подтверждённых данных.** Это учебный кейс анализа и проектирования решения, а не система, внедрённая на реальной площадке. Модель AS-IS и описанные проблемы являются гипотезами кейса, а не результатами интервью с заинтересованными сторонами. В репозитории находятся контракт OpenAPI и средства тестирования mock-сервера, но нет производственного backend. Фактический эффект для бизнеса не измерялся.

## 1. Бизнес-контекст и формулировка проблемы

Площадке, организующей VIP-мероприятия, необходимо координировать несколько связанных действий: регистрировать бронирование, назначать кабинку, организовывать дополнительные услуги, распределять сотрудников и проверять расписание на день мероприятия. Эти действия зависят от общих ресурсов, времени, статусов и правил доступности.

Если сведения о мероприятиях и назначениях хранятся в отдельных таблицах, чатах или личных рабочих процессах, координаторам приходится вручную сопоставлять информацию. Это создаёт риск неполных данных бронирования, двойного назначения ресурсов, позднего обнаружения конфликтов и несогласованных решений о готовности мероприятия к подтверждению.

**Проблема:** как сделать координацию VIP-мероприятий более последовательной и предсказуемой, определив единый жизненный цикл мероприятия, явные правила назначения ресурсов и повторяемый способ выявления конфликтов расписания?

Бизнес-проблема заключается не в том, что «площадке нужен API». API — лишь один из возможных способов реализовать более прозрачный процесс. Поэтому анализ начинается с бизнес-сценария и правил, а затем переводится в требования и проверяемый контракт интерфейса.

## 2. AS-IS и TO-BE: краткий обзор

### AS-IS — гипотеза текущего состояния

1. Поступает запрос клиента, координатор записывает данные мероприятия.
2. Координатор проверяет доступность кабинки по имеющейся информации.
3. Организуются услуги и назначаются сотрудники; сведения могут храниться в разных записях или переписках.
4. Расписание на день составляется на основе данных о мероприятиях и ресурсах.
5. Недостающие сведения и пересечения устраняются, когда кто-то их обнаруживает.

**Потенциальные проблемы для проверки:** разрозненность информации, неодинаковые проверки, неясные правила смены статусов и позднее выявление конфликтов по кабинкам или сотрудникам. Это гипотезы, а не подтверждённые факты о реальном бизнесе.

### TO-BE — предлагаемое целевое состояние

1. Зарегистрировать мероприятие в статусе `DRAFT`.
2. Проверить обязательные данные бронирования.
3. Найти подходящую кабинку и проверить доступность перед назначением.
4. Добавить необходимые услуги и назначить сотрудников.
5. Проверить расписание и выявить пересечения или недостаточные интервалы между активностями.
6. Подтвердить мероприятие только при допустимом переходе статуса и выполнении согласованных условий.
7. Возвращать структурированные ошибки, если данные некорректны, ресурс недоступен или операция нарушает бизнес-правило.

TO-BE — предлагаемая модель, которую необходимо согласовать с заинтересованными сторонами до реализации.

## 3. Цели бизнеса и критерии успеха

| Цель | Ожидаемый результат | Как измерять после внедрения |
|---|---|---|
| Повысить полноту и согласованность данных | Бронирования проходят проверку обязательных полей | Доля бронирований, прошедших проверку |
| Сократить конфликты ресурсов | Конфликты кабинок и сотрудников выявляются до проведения мероприятия | Число подтверждённых конфликтов за период |
| Обеспечить контроль жизненного цикла | Недопустимые переходы статусов не принимаются | Целевое значение — ноль принятых недопустимых переходов |
| Повысить прозрачность расписания | Координатор может получить расписание и список обнаруженных конфликтов | Доля релевантных конфликтов, выявленных при проверке |
| Стандартизировать обработку ошибок | Ошибки имеют единый формат и машиночитаемые коды | Доля сценариев, возвращающих ожидаемый код и структуру |

Это предлагаемые показатели, а не достигнутые результаты. Базовые значения, целевые значения, период измерения и источники данных должны быть согласованы с владельцем бизнеса.

## 4. Заинтересованные стороны и их потребности

| Роль | Основной интерес | Потребность |
|---|---|---|
| Руководитель площадки | Точность бронирований и контроль обязательств | Регистрировать и подтверждать мероприятия при соблюдении правил жизненного цикла |
| Координатор мероприятий | Доступность ресурсов и полнота информации | Назначать кабинки, услуги и сотрудников, проверять конфликты |
| Операционная команда | Реалистичное и непротиворечивое расписание | Выявлять пересечения назначений и недостаточные временные интервалы |
| Команда разработки | Однозначные функциональные и интерфейсные требования | Реализовать документированные операции, проверки и ошибки |
| QA / тестировщик | Проверяемое ожидаемое поведение | Проверять позитивные и негативные сценарии по критериям приёмки |

Роли и потребности предложены для учебного сценария. В реальном проекте их нужно подтвердить интервью, воркшопами и анализом существующих документов.

## 5. Границы проекта

### Входит в объём

Контракт API охватывает пять функциональных областей и 13 операций.

| Область | Возможности бизнеса | Операции |
|---|---|---|
| Мероприятия | Получение, регистрация, изменение данных и статуса | `GET /events`, `POST /events`, `GET /events/{eventId}`, `PATCH /events/{eventId}`, `PATCH /events/{eventId}/status` |
| Кабинки | Поиск доступных кабинок и назначение кабинки | `GET /cabins`, `PUT /events/{eventId}/cabin` |
| Услуги | Получение и добавление услуг мероприятия | `GET /events/{eventId}/services`, `POST /events/{eventId}/services` |
| Персонал | Просмотр назначений и назначение сотрудников | `GET /events/{eventId}/staff`, `POST /events/{eventId}/staff` |
| Расписание | Просмотр расписания и поиск конфликтов | `GET /schedule/{date}`, `GET /schedule/{date}/conflicts` |

### Не входит в объём

- Производственный backend и постоянное хранение данных.
- Аутентификация, авторизация и разграничение доступа по ролям.
- Пользовательский интерфейс для руководителей и координаторов.
- Интеграции с внешними системами кейтеринга, оплаты или управления персоналом.
- Уведомления в реальном времени.
- Производственное развёртывание, мониторинг и эксплуатационная поддержка.

Эти ограничения намеренные: цель проекта — продемонстрировать бизнес-анализ и спецификацию требований, а не разработку backend.

## 6. Функциональные требования и бизнес-правила

### Управление мероприятиями

- Система должна позволять получать список мероприятий за указанную дату.
- Система должна позволять регистрировать мероприятие.
- Новое мероприятие должно получать статус `DRAFT`.
- Система должна позволять просматривать и изменять данные мероприятия.
- Некорректные данные должны отклоняться согласно документированным правилам проверки.
- Смена статуса разрешена только по допустимым переходам жизненного цикла.

### Назначение ресурсов

- Система должна предоставлять возможность искать кабинки по заданным параметрам времени.
- Система должна поддерживать назначение кабинки мероприятию.
- Если бронирование кабинки пересекается с существующим, система должна возвращать конфликт.
- Система должна поддерживать назначение сотрудников мероприятию.
- Если назначение сотрудника пересекается с другим назначением, система должна возвращать конфликт.

### Расписание

- Система должна предоставлять расписание на указанную дату.
- Система должна предоставлять операцию проверки конфликтов.
- Ответ проверки конфликтов должен поддерживать описание пересечений бронирований одной кабинки, пересечений назначений сотрудников и недостаточных интервалов между активностями.

### Обработка ошибок

Ошибки должны иметь документированную структуру: машиночитаемый код, понятное сообщение и, при необходимости, дополнительные сведения. Контракт различает некорректные запросы, отсутствующие ресурсы, бизнес-конфликты и ошибки валидации.

### Жизненный цикл мероприятия

Предлагаемая последовательность:

`DRAFT → CONFIRMED → IN_PROGRESS → COMPLETED`

Подтверждённое мероприятие также может перейти в `CANCELLED`. Полную матрицу переходов и исключения необходимо согласовать с бизнес-заказчиком до реализации.

## 7. Примеры критериев приёмки

Критерии приёмки описывают наблюдаемые условия, при выполнении которых требование можно считать удовлетворённым.

### AC-01: Создание мероприятия

**Дано:** пользователь передаёт корректные обязательные данные мероприятия.  
**Когда:** отправляет запрос на создание мероприятия.  
**Тогда:** контракт возвращает `201 Created`, идентификатор мероприятия и статус `DRAFT`.

**Негативный сценарий:** если данные некорректны, система возвращает документированный ответ об ошибке валидации.

### AC-02: Отклонение недопустимого перехода статуса

**Дано:** мероприятие находится в статусе `COMPLETED`.  
**Когда:** пользователь пытается изменить статус на `CONFIRMED`.  
**Тогда:** операция отклоняется с `409 Conflict` и кодом `INVALID_STATUS_TRANSITION`.

### AC-03: Предотвращение конфликта бронирования кабинки

**Дано:** кабинка уже забронирована на определённый интервал времени.  
**Когда:** пользователь пытается назначить ту же кабинку мероприятию с пересекающимся интервалом.  
**Тогда:** назначение отклоняется с `409 Conflict` и кодом `CABIN_ALREADY_BOOKED`.

### AC-04: Предотвращение конфликта назначения сотрудника

**Дано:** у сотрудника уже есть назначение, пересекающееся с запрашиваемым интервалом.  
**Когда:** пользователь пытается назначить сотрудника на другую конфликтующую активность.  
**Тогда:** назначение отклоняется с `409 Conflict` и кодом `STAFF_ALREADY_ASSIGNED`.

### AC-05: Проверка времени мероприятия

**Дано:** запрос содержит время начала и окончания.  
**Когда:** время окончания не позже времени начала.  
**Тогда:** система отклоняет запрос с документированным ответом об ошибке валидации.

Полный набор историй и критериев приёмки приведён в [`traceability.md`](traceability.md).

Матрица прослеживаемости связывает бизнес-потребности с пользовательскими историями, операциями API, критериями приёмки и сценариями проверки.

Она помогает:

2. **Проверить согласованность:** выявлять противоречия между требованиями, бизнес-правилами и контрактом API.

## 9. Предположения, ограничения и открытые вопросы

### Текущие предположения

- Площадка проводит несколько мероприятий и использует общие кабинки и персонал.
- У мероприятия есть дата, время начала и окончания, а также количество гостей.
- Конфликт ресурсов определяется пересечением временных интервалов.
- Мероприятия проходят управляемый жизненный цикл.
- API — предлагаемая интеграционная граница будущего решения, а не существующий производственный сервис.

### Открытые вопросы для заказчика

1. **Создание мероприятия:** можно ли назначить кабинку при создании мероприятия или это отдельный шаг?
2. **Подтверждение:** какие сведения обязательны, прежде чем переводить мероприятие из `DRAFT` в `CONFIRMED`?
3. **Политика конфликтов:** запрещены ли все пересечения назначений или существуют исключения?
4. **Буфер между активностями:** какой минимальный интервал нужен и зависит ли он от типа активности?
5. **Требования к персоналу:** какие роли, квалификации и ограничения доступности учитывать?
6. **Отмена:** что происходит с уже назначенными услугами и сотрудниками при отмене мероприятия?
7. **Параллельные операции:** что делать, если два координатора почти одновременно пытаются забронировать один ресурс?

Эти решения необходимо принять до реализации, поскольку они влияют на модель данных, проверки, процесс и критерии приёмки.

## 11. Mock-сервер и проверка контракта

В репозитории нет производственного backend. Prism использует спецификацию OpenAPI для имитации ответов, а Postman отправляет запросы и проверяет ответы.

Для запуска mock-сервера нужен Node.js. Выполните команду из папки проекта:

```bash
npx @stoplight/prism-cli mock event-management-api.yaml
```

Сервер по умолчанию доступен по адресу `http://127.0.0.1:4010`.

Пример запроса:

```bash
curl "http://127.0.0.1:4010/events?date=2026-11-14"
```

Запуск коллекции через Newman:

```bash
npx newman run event-management-api.postman_collection.json --env-var "baseUrl=http://127.0.0.1:4010"
```

Коллекция содержит 18 запросов и рассчитана на 36 проверок: проверки HTTP-статусов, структуры ответов и документированных кодов ошибок.

**Ограничение тестирования:** успешный прогон на mock-сервере подтверждает согласованность запросов, ответов и примеров со спецификацией. Он не доказывает работу бизнес-логики в реальной системе. Сохранение данных, защита от параллельного бронирования и фактическое обнаружение конфликтов должны проверяться на реализованном backend.

## 12. Итог проекта

Проект демонстрирует аналитическую цепочку от бизнес-проблемы к документированному и проверяемому проектному решению:

- сформулирован учебный бизнес-сценарий и определены потенциальные операционные риски;
- описаны гипотетический AS-IS и предлагаемый TO-BE;
- определены цели, заинтересованные стороны и границы проекта;
- формализованы пользовательские потребности, бизнес-правила и критерии приёмки;
- выделены предположения и нерешённые бизнес-вопросы;
- требования связаны с операциями API и сценариями проверки;
- контракт интерфейса описан в OpenAPI;
- подготовлены mock-среда и коллекция Postman для проверки контракта.

Главный результат — **документированная и проверяемая модель решения**, а не развёрнутая бизнес-система и не измеренный эффект для бизнеса.

Следующий шаг в реальном проекте — проверить модель AS-IS и бизнес-правила с заинтересованными сторонами, закрыть открытые вопросы и согласовать измеримые критерии успеха до реализации.
